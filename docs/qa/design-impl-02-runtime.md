## Scope and evidence

This is a source review of the current Practice run and diagnostic handoff, not a browser or physics-fidelity acceptance. The relevant implementation is `SpikeSimulatorWindow.svelte` (`startRobot`, `stopRobot`, `PracticeReadinessShell` wiring), `SpikeSimulator.svelte` (`startOrPauseSimulation`, `stepVM`, `stopRun`, `togglePause`, `resetRun`, `recordCompletedFixedSteps`), `vm.ts` (`VM`, `Thread`), `simulation.ts` (`advance`, `reset`, `dispose`), `run-log.ts`, and `RunLogConsole.svelte`. The requested Slice 3 states and later structured diagnostic event design are in `docs/design/simplified-practice-ui-spec.md` and `docs/qa/ui-platform-16-diagnostics.md`.

## Existing event and state contract

-   **Run request:** The parent checks readiness, generates Blockly code, writes `codeStore`, then sets bound `runSimulation = true`. The child clears the shared log, stops the previous VM, compiles the copied scene, creates/starts a new VM, awaits `Simulation.create`, and starts an animation-frame loop. A generation check discards a late physics world after Stop/new start. The boolean remains true through initialization, execution, pause, VM stop, and failure, so it is not a result state.
-   **Fixed-step progress:** `Simulation.advance` steps physics and calls `vm.step` on each fixed step. `recordCompletedFixedSteps` increments `diagnosticElapsedSeconds` from completed steps, advances the match clock, and samples motion/contact about every 0.5 simulated seconds. Use this time for result timing; each sample is an observation at one instant.
-   **Pause/resume:** `togglePause` calls `vm.pause`/`unpause`, toggles local `simulationPaused`, and logs a message. The frame loop exits while the VM is not running; resume schedules another frame. `stepVM` currently logs a `VM loop stopped` warning even for `paused`, though it suppresses a result while `simulationPaused` is true.
-   **Stop:** The inner Stop sets a `stopped` result and clears `runSimulation`; the parent `Stop run` only clears the boolean. The child's reactive false path may create a stopped result, disposes the simulation, calls `vm.stop`, and clears the match. `ScenePreview` is rendered only while `runSimulation` is true, so Stop swaps the table for `RobotPreview`; the stopped scene is not available for physics inspection.
-   **Reset:** With a simulation, `resetRun` restores its physics/hub snapshot, stops/starts the same VM, resets VM timer and match state, clears the result, zeros diagnostic elapsed time, and schedules a frame. Without a simulation, it may request a new run if ready or show a setup-blocked result. This is distinct from Stop and project restore. It does not clear `lastDiagnosticSeconds` or identify a new run in the log.
-   **VM completion and failure:** Individual threads become `stopped` when their generator finishes; `VM.state` stays `running` until `VM.stop` is called. Event hats can remain eligible for later triggers. `stepVM` maps a non-running VM to a diagnosis-based result, and its catch maps any loop exception to `startup-failure`. The initialization catch logs an error and cleans up but sets no result or `runSimulation = false`. Normal one-shot thread completion does not stop the VM; startup failure can leave the UI saying Running; later execution failure can be mislabeled as startup failure.
-   **Run log:** `appendRunLog` stores `{id, timestamp, level, message}` in a global Svelte store, capped at 500. `timestamp` is locale wall-clock text. New runs clear it; manual Clear removes it. The console derives guidance from the most recent warning/error independently of the current result; filters and text export use visible entries in newest-first order. Raw text has no run ID, typed lifecycle reason, or fixed-step timestamp, and should not be parsed into a terminal result.

The existing `PracticeResultKind` names (`completed`, `stopped`, `waiting`, `motors-off`, `suspected-obstruction`, `startup-failure`) are **presentation labels**, not VM lifecycle events. `resultForDiagnosis` evaluates one motion sample only after the VM becomes non-running. It maps some contact/motor observations to result labels and otherwise returns `completed`; it cannot establish why execution ended. `waiting` and `motors-off` are observations that may occur while a program is still running. A contact pair must not be described as the cause of a stop.

## Safe Slice 3 additions

1. Introduce one run-local lifecycle record at the owning component boundary, with an attempt ID/generation, phase (`preparing`, `running`, `paused`, `ended`), simulation elapsed seconds, and an explicit end reason (`user-stop`, `program-complete`, `startup-failure`, `runtime-failure`, `match-timeout`, or `cancelled/replaced`). Emit each terminal result once. Keep the public `runSimulation` binding for incremental compatibility, but derive the card and controls from the lifecycle record instead of treating that boolean or a diagnostic string as a terminal cause. If Slice 3 cannot safely add a trustworthy program-complete signal, keep the run active and label the observed idle state; do not fabricate `Run finished`.
2. Route the parent and inner Stop through the same child/controller action. Record user stop and elapsed fixed-step time **before** cleanup, then stop the VM once. Retain a read-only final scene/physics view if the UI promises inspection, or explicitly change the promise until that state can be retained. Keep pause and result distinct; a paused VM should not create a warning or terminal card merely because the animation loop is idle.
3. Define a genuine completion boundary before using `completed`: one-shot program-start work and its awaited/broadcast child work have settled, with no active commands; event watchers must be handled deliberately. Thread completion by itself is insufficient when other stacks or event hats remain. Keep `waiting` and `motors-off` as observed status with a next action unless the run also has an independently known terminal reason. Match timeout and explicit M01 finish should remain distinct from normal program completion and scoring availability.
4. Set a visible failure result in the initialization catch, and separate runtime loop errors from setup/start errors. Normalize messages to a recoverable participant summary while keeping the exact exception in diagnostics. Set the run phase/controls consistently, and clean up only resources owned by the failed attempt. Guard asynchronous `Simulation.create` continuations and animation callbacks with the same attempt identity; a stale callback/catch must not stop or relabel a newer run.
5. Preserve `RunLogEntry` and `formatRunLogEntries` behavior. Add optional run ID, fixed-step time, and typed lifecycle/observation fields alongside raw text as a follow-up contract; do not parse body IDs from free-form text in the result UI. This aligns with the proposed `DiagnosticEventV1` in `docs/qa/ui-platform-16-diagnostics.md`. Opening Developer Diagnostics should select the diagnostics workspace and show the same run's raw entries without clearing them. Manual log Clear should clear raw evidence only, not silently change the lifecycle result; a new attempt should explicitly reset both the result and its run-local diagnostic selection.

## Blockers and acceptance criteria

**Slice 3 result blockers**

-   There is no VM program-complete event or settled-work API. The current stopped-VM fallback cannot support a truthful `completed` card. Runtime ownership is required for a completion signal; `fll_experience` should not infer it from `vm.state`, motor state, or a contact message.
-   Parent Stop and inner Stop are separate entry points, and stop currently disposes the world/changes the preview. Align their event contract before promising post-stop scene inspection.
-   Initialization and frame-loop failures do not make lifecycle state and controls agree. The first catch leaves `runSimulation` true without a result; the second calls a runtime failure `startup-failure`.
-   Diagnostics lack a structured run/event identity. Slice 3 can provide a deliberate route to existing raw logs, but exact-ID contact inspection and an immutable event snapshot belong to the later diagnostic event contract.

**Acceptance scenarios for implementation and independent QA**

1. A ready one-shot program starts once and either reaches a verified settled-work completion event or remains explicitly running/idle; it never shows `Run finished` merely because all motors are off. Two concurrent stacks must not report completion until both settle. An event hat waiting for another trigger is represented deliberately.
2. Stop from either control produces one `user-stop` result at the same fixed-step time, halts VM/motors, and retains exactly the advertised inspection state. Repeated Stop is idempotent. Pause/resume changes no elapsed simulation time during the hold and produces no terminal warning/card.
3. Startup failure before or during `Simulation.create` leaves neither a Running label nor active controls; it shows a useful reason and retains the exact diagnostic error. A failure after running begins is labeled as runtime failure. Rapid Start–Stop–Start and unmount during pending creation/frame callbacks do not let old work stop, dispose, or relabel the new attempt.
4. Reset from active, paused, stopped, and failed states returns physics, hub, VM, match clock, and result to the documented attempt boundary; one frame loop remains. Diagnostic elapsed time and sample cadence restart together. Repeating Reset yields the same starting state.
5. A sampled contact, stationary robot, or motors-off state remains observation-based. The result never claims contact caused the stop or that a mission was scored. Preserve body IDs and raw text where available; if contact data is absent, no object inspection action is offered.
6. The result is understandable without opening raw logs. `Open diagnostics` changes to Developer Diagnostics without clearing evidence; warning/error guidance, newest-first filters, and filtered text export continue to work. Clearing raw logs does not erase an already displayed result. Verify this flow in a browser on the combined UI patch.

Use bounded simulated-time VM/simulation tests for the completion, concurrent-stack, stop/reset, and stale-attempt cases. Browser QA is needed for control visibility, the stopped-scene promise, route/focus behavior, and export. Existing run-log tests cover append/cap/clear/format/guidance only; they do not validate lifecycle transitions. Numerical tests do not establish physical calibration or official scoring.
